# 06 · 双重认证与外驱协同协议 (Dual-Agent Consensus & Safe Fallback)

> 解决内部 MiniMax 算力额度不可持续问题，并防范低端外部 Agent/模型对项目现状的误解与较差规划。

---

## 1. 核心背景与设计哲学

在长周期、多端协作的 AI 辅助软件开发中，依赖单一模型存在两大致命缺陷：
1. **内部配额单点瓶颈（SPOF）**：MiniMax 算力套餐具备 5 小时滚动窗口和每周限额，一旦额度打满、网络波动或欠费，基于内部模型的自主规划即刻瘫痪。
2. **外部弱模型劣质规划（Weak Agent Risk）**：当放开接口让外部各类型模型（廉价小模型、不同厂商模型或第三方客户端）直接驱动任务时，弱模型极易出现**理解偏差**（如幻觉规划已存在或不存在的模块、破坏前置依赖顺序、不写测试验证、随意将未完成的任务标记为 Done）。

**HPF Work Manager 的解决方案：双重认证协同（Dual-Agent Consensus）+ 确定性护栏降级（Deterministic Guardrails）**。

## 2. 动态驱动状态机

管理器会依据 MiniMax 算力窗口实时判定工作模式：

| 模式 | 触发条件 | 规划机制 | 验收机制 | 认证签章 (`certified_by`) |
|---|---|---|---|---|
| **`DUAL_CERTIFIED`** (双重认证模式) | 内部 5h 剩余额度 > 5% 且 API 响应健康 | **外部提案 + 内部 MiniMax 交叉审查**：内部架构师纠偏低端模型幻觉，补充缺失测试要求 | 必须附带 `git_ref` 与测试日志，由系统归档并盖双章 | `["external_agent", "internal_MiniMax-M3.1-Flash-Preview"]` |
| **`EXTERNAL_DRIVEN`** (外驱安全护栏模式) | 内部额度耗尽（<=5%）、429 限流或网络异常 | **外部 Agent 驱动 + 静态规则护栏**：启发式规则分析代码库结构（零 Token），强制格式与验收契约 | 强约束 `git_ref`（7-40位 Commit SHA）与真实执行凭据 | `["external_agent", "manager_guardrails_engine"]` |

## 3. 核心工具与协议规范

### 3.1 探活与状态感知：`get_manager_status`
外部 Agent 在开启任何重大规划前，**首选调用该接口获取当前环境指令**：
- **返回字段**：
  - `driver_mode`: `"DUAL_CERTIFIED"` 或 `"EXTERNAL_DRIVEN"`
  - `has_internal_tokens`: 是否有内部可用 Token
  - `quota`: 包含 `remaining_percent`, `minutes_left`, `reset_time_str`, `is_night_shift`
  - `guidelines`: 动态下发给当前 Agent 的行为准则 Prompt

### 3.2 规划推演：`get_next_steps(project_name)`
- **双重认证时**：内部 MiniMax 深入阅读当前项目的目录树、最新 Commit、README、TODO 注释，推演生成 3 个最契合当下工程诉求的 Next Steps。
- **降级模式时**：自动激活**代码库启发式规则推演引擎**：
  1. 探测是否缺少 `tests/` 目录或自动化测试套件；
  2. 提取源代码中未闭环的 `TODO/FIXME`；
  3. 分析最新一次 Git Commit 语义延伸下游接入与重构任务；
  4. 绝不报错崩溃，返回结构完备的保底任务。

### 3.3 提案审查与落盘：`propose_task_plan`
外部 Agent 绝不应未经论证直接批量调用底层 `create_task`。推荐将规划构想打包提交给 `propose_task_plan`：
- **输入参数**：
  - `project_name`: 目标项目名
  - `tasks`: 提议的任务数组（包含 `title`, `description`, `category`, `priority`, `estimated_hours`）
  - `agent_role_or_id`: 当前外部 Agent 标识（如 `cursor-claude-3.5`, `antigravity-gemini`, `dsh-qwen`）
  - `rationale`: 外部 Agent 提出此规划的推演动机
  - `auto_create`: 审核通过后是否直接在数据库看板建档
- **处理流**：
  - 内部架构师模型对提案逐项检查：
    - 是否规划了与当前代码架构无关的虚构模块？
    - 是否漏掉了单元测试与错误处理？
    - 优先级（high/medium/low）与工时是否合理？
  - 输出 `audit_status` (`APPROVED` / `MODIFIED` / `REJECTED`) 与每一项任务的判定及优化后 Prompt。

### 3.4 交付核销与防虚标：`verify_and_complete_task`
为了防止低端 Agent 在未写代码或测试未跑通时盲目将任务置为 `done`：
- **必填证据链**：
  - `task_id`: 任务编号
  - `git_ref`: 必须为有效的 Commit Hash（如 `4a9fbf0`）或稳定分支引用
  - `verification_evidence`: 测试执行输出、边界验证日志或改动核心代码片段（不少于 5 字符）
  - `summary`: 完成情况概述
- **原子联动**：
  1. 将任务标记为 `done` 并盖章 `completed_at`；
  2. 自动在本项目内创建一条 `entry_type="progress"` 的 **DevLog**，将代码凭据永久固化；
  3. 通过 SSE 广播至前端 Cockpit，看板实时更新。

## 4. 低端 Agent 防御防线（Guardrails Checklist）

当外部接入的是小参数或免费模型时，系统内置以下防线：
1. **反空头描述**：任务描述少于 15 字符会被规则拦截或自动注入执行规范与验收标准模板。
2. **反随意删除**：MCP 服务中 `delete_task` 需显式确认，并在文档中明令禁止 Agent 随意执行删除。
3. **依赖成环拦截**：调用 `add_task_dependency` 时底层自动运行拓扑环检测算法，成环立即报 `ValueError`。
4. **归属隔离**：任何任务或关联引用的 task ID 必须严格属于当前项目与当前用户，严禁跨项目乱窜。

## 5. 典型协作工作流代码示例

### 场景：外部 Agent 主导一个功能演进并走双重认证

```python
# 1. 探活当前管理器模式
status = get_manager_status()
print(status["driver_mode"])  # => DUAL_CERTIFIED 或 EXTERNAL_DRIVEN

# 2. 获取项目当前推演建议或提出自己的计划
my_proposal = [
    {
        "title": "实现任务完成双重认证核验与自动写入 DevLog",
        "category": "feature",
        "priority": "high",
        "estimated_hours": 3,
        "description": "【目标】编写 verify_and_complete_task 接口\n【验收标准】单测通过并产生对应 DevLog"
    }
]

# 3. 提交双重认证审查并直接落入看板
review = propose_task_plan(
    project_name="hpf-work-manager",
    tasks=my_proposal,
    agent_role_or_id="cursor-agent",
    rationale="解决低端模型盲目标记完成问题",
    auto_create=True
)
task_id = review["created_task_ids"][0]

# 4. 编码与测试...
# (本地跑通 pytest，完成 git commit: 8f2c3d1)

# 5. 提供证据完成核销与归档
receipt = verify_and_complete_task(
    task_id=task_id,
    git_ref="8f2c3d1",
    verification_evidence="pytest backend/tests/test_tasks.py 全部 PASS (8 passed)",
    summary="已完成双重认证核销逻辑并在 MCP 层注册工具"
)
print(receipt["message"])
```
