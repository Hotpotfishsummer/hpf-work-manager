# 05 · AI 编码工作流

> 面向 AI 工具的推荐使用方式。核心原则：**任务/里程碑管结果，DevLog 管过程**；
> 动手前先恢复上下文，动完手随手记录，收尾时出汇报。

## 1. 标准会话流程

### 1.1 新项目/新任务规划

```
1. list_projects                        # 找到或确认项目
2. create_project(name, start_date, end_date)     # 无项目时创建
3. create_milestone(project_id, name, due_date)   # 划分里程碑
4. create_task(...)  × N                # 建任务（priority/status/due_date）
5. add_task_dependency(task_id, depends_on_task_id)  # 有先后顺序时建依赖
```

任务粒度建议：可独立验收的最小交付单元；`due_date` 尽量给，延期预警才有意义。

### 1.2 日常编码会话

```
1. list_projects → get_project_state(project_id)     # 恢复上下文（必做）
2. start_dev_session(project_id, title)              # 开启本次会话
3. list_tasks(project_id, status="todo")             # 拉全量待办
   list_tasks(project_id, status="in_progress")      # + 进行中：建立"历史待办"对账基线
4. 编码过程中：
   - 旧任务被本次工作覆盖 → get_task 确认后 update_task(status="done"/进度, git_ref=commit)  # 先对账，不重复建任务
   - 新工作无对应任务   → create_task                                  # 仅当确无旧任务对应时才新建
   - 阶段性进展 → log_progress(..., git_ref=commit)
   - 踩坑 → log_difficulty / log_blocker
   - 决策 → log_decision
   - 下一步 → log_todo
5. end_dev_session(session_id, summary)              # 收口
```

> **历史任务对账（重要）**：不要只建新任务、留着旧账不动。会话开始拉全量
> `todo`/`in_progress` 后，凡本次开发实际覆盖到的旧任务（有代码/commit 证据），
> 都主动 `update_task` 推进其状态或进度；绝不 `delete_task`（不可逆）。

> 为什么先 `get_project_state`？它会一次性返回：项目信息、进行中会话、
> 未完成待办/难点/阻塞、最近进展与决策 —— 新机器/新会话无需翻历史。

### 1.3 阶段汇报

```
get_project_stats_mcp(project_id)   # 数字：进度%、延期清单
get_burndown_mcp(project_id)        # 趋势：期望 vs 实际
get_dev_report(project_id)          # 过程：按类型分组的 Markdown
```

三者的组合即完整汇报：**结果 + 趋势 + 过程**。

## 2. 场景示例（端到端）

### 场景 A：为项目补一个功能并全程记录

```
# 恢复上下文
get_project_state(project_id=1)
# => project: 官网改版 / active_session: null / open_todos: [...] ...

# 建任务（若项目里还没有）
create_task(project_id=1, name="实现搜索功能", priority="high",
            milestone_id=2, due_date="2026-08-20")
# => { "id": 42, "status": "todo", "progress": 0, ... }

# 开始会话
start_dev_session(project_id=1, title="实现搜索功能")
# => { "id": 9, ... }

# 完成主体后：更新任务结果
update_task(task_id=42, status="done")
# => { "id": 42, "status": "done", "progress": 100, "completed_at": "..." }

# 若历史任务（前几次会话建的）被本次工作顺手完成，同样直接更新，不要另建任务
update_task(task_id=17, status="done", git_ref="48fcc34")

# 记录过程
log_progress(project_id=1, title="完成搜索接口与前端接入", git_ref="9f3a2b1")
log_difficulty(project_id=1, title="中文分词方案反复", severity="medium",
               content="最终用 jieba 全模式 + 缓存，满足当前量级")
log_todo(project_id=1, title="搜索相关性排序后续优化")

# 收口
end_dev_session(session_id=9, summary="完成搜索功能：接口+前端+单测，遗留排序优化")
```

### 场景 B：跨机器接续开发

```
# 新机器上：先看项目状态，再决定从哪继续
list_projects()                         # 找到项目 id
get_project_state(project_id=1)         # 看到 active_session 与 open_blockers

# 如果上个会话未收口：先结束它
end_dev_session(session_id=上次的active_session.id, summary="交接：已完成 X，下一步 Y")

# 再开新会话
start_dev_session(project_id=1, title="续：搜索排序优化")
```

### 场景 C：给协作同事/领导出汇报

```
get_project_stats_mcp(project_id=1)
get_burndown_mcp(project_id=1)
get_dev_report(project_id=1, start="2026-08-01", end="2026-08-13")
```

## 3. 职责边界（AI 使用清单）

| 该做的 | 不该做的 |
|---|---|
| 完成任务即 `update_task(status="done")` | 不要手动把 `progress` 改成 100（自动） |
| 旧任务被本次工作覆盖时主动 `update_task`（需 git_ref/代码证据） | 不为已有任务重复建新任务；不盲目 `delete_task`（不可逆） |
| 顺手写 DevLog 过程记录 | 不要用 DevLog 代替任务追踪 |
| 新会话先 `get_project_state` → `list_tasks` 对账历史待办 | 不要凭记忆假设任务 id；不要只建新任务留旧账 |
| 改状态前先 `get_task` 确认 | 不要盲目 `delete_*`（不可逆） |
| 多工具各配独立 API Key | 不要共享 key、不要写死在代码仓库 |

## 4. 注意事项

- **数字与枚举**：`status`/`priority`/`severity`/`entry_type` 均为限定枚举，非法值直接报错。
- **日期格式**：一律 `YYYY-MM-DD`（ISO）。
- **ID 归属**：`related_task_ids`、`milestone_id`、`depends_on_task_id` 必须是本项目内实体。
- **实时性**：写操作会 SSE 推送到前端，无需再调一次刷新。
- **幂等判断**：依赖已存在、任务重复依赖等会报错，先查再写。
